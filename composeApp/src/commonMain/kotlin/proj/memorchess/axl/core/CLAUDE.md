# Core layer (`core/`)

Platform agnostic logic for the board, the opening graph, and spaced repetition. Persistence sits behind an interface. There is no `SyncEngine` yet, but the local stores already carry what one needs: every node and edge write is soft deleted and stamped with the four sync fields (`isDeleted`, `updatedAt`, `originDevice`, `deviceSeq`), and a per key outbox records what is dirty. Three read only HTTP clients reach outward today: the Lichess opening explorer, Lichess study import, and the repertoire catalog served as static files from the `repertoire-data` branch on raw GitHub.

- **`engine/`** — chess engine wrapper around the `chess-core` library (`io.github.alluhemanth:chess-core`). `GameEngine` is the central class: it owns board state, validates moves (SAN and coordinate-based), handles promotions, and produces position FENs. Two value classes matter: `Fen` (the full 6-part FEN string) and `PositionKey` (a FEN cropped of its move counters — the graph key). Helper types: `Player`, `ChessPiece`, `PieceKind`, `BoardLocation`, `TileColor`. Everything in this package except `evaluation/` now lives in the `:shared` module under the same package name, so the server can use it too. `evaluation/` stays here because it is the only user of `stockfish-multiplatform`.
- **`graph/`** — the opening tree, keyed by `PositionKey`. `OpeningTree` is a pure in-memory graph of immutable `Node` and `Edge` values. **`TreeStore` is the single mutation chokepoint**: it wraps `DatabaseQueryManager`, owns the cached `OpeningTree`, and is what UI, interactions, and scheduling code talk to — never mutate the graph anywhere else. On every write path it also stamps the row with its `DeviceIdentity`; the touched key is then marked dirty in the outbox, mostly by the `DatabaseQueryManager` call that writes the row (in the same transaction as that write) and, for a newly added edge, by `TreeStore` itself — pushing that outbox is `SyncEngine`'s future job. `TrainingScheduler` drives spaced repetition through `TreeStore` and `SchedulingAlgorithm`. `NavigationHistory` handles back/forward navigation over `PositionKey` and `Edge` values, `TrainingEntry` is a lightweight reference to a trainable position, and `NodeState` is the position-state enum. `DeleteMode` (`HARD`/`SOFT`) selects deletion semantics; `SOFT` is the default now that a tombstone may need to reach another device, and `HARD` survives for local only cleanup (tests, and callers that want a position gone without a tombstone) — `eraseAll` is a separate method that wipes everything unconditionally rather than routing through `DeleteMode`. `PreviousAndNextMoves` exists at the persistence seam only, as a DTO for `DatabaseQueryManager`, and `MoveInsertion` (declared in `TreeStore.kt`) is the batch insert argument. `Edge` is the immutable edge value, carrying `originDevice`/`deviceSeq` alongside its existing `updatedAt`/`isDeleted`. `GraphSerializer` reads and writes a graph as deterministic tab separated text.
- **`interactions/`** — game interaction controllers. The abstract `InteractionsManager` handles tile selection, move execution, and the promotion flow; `LinesExplorer` (free exploration, talks to `TreeStore`), `SingleMoveTrainer` (spaced repetition training, talks to `TrainingScheduler`) and `RepertoireExplorer` (read only navigation of one downloaded repertoire over a throwaway `TreeStore`, rejecting off book moves) implement it.
- **`data/`** — the low level persistence seam. `DatabaseQueryManager` is implemented by a Room backed store in `nonJsMain`, an IndexedDB backed one in `wasmJsMain` (`IndexedDbInstance`), and `InMemoryDatabaseQueryManager` for tests and transient graphs. Only `TreeStore` and those implementations may touch its node and move surface; `ConfigItem` implementations also call `markDirty` directly, to queue a setting's `SettingKey`, since a setting has no row of its own for `TreeStore` to write through. `DataNode` and `DataMove` are the row DTOs (each carrying `isDeleted`, `updatedAt`, `originDevice`, `deviceSeq`), `PositionKey` the cropped FEN key, `NodesPage` the bounded paging result, `SchedulingCounts` the daily tallies, and `BoundedDescendants` the capped breadth first descendant count shared by every backend so the convergence rule cannot drift. `DirtyKey` is the outbox key union (`NodeKey`/`EdgeKey`/`SettingKey`); `OutboxEntry` pairs one with the `deviceSeq` of the write it names. `DatabaseQueryManager.markDirty`/`getOutbox`/`clearDirty` are its read/write surface, backed by a dedicated Room entity (`OutboxEntryEntity`) and IndexedDB store, queuing keys rather than rows so repeat edits collapse. Every row write that changes a node or a move (`insertNodes`, `deletePosition`, `deleteMove`) queues its own outbox entry in the same transaction as the row it names, so a kill between the two can never drop one relative to the other; `clearDirty` only removes an entry whose queued `deviceSeq` has not moved past the one actually pushed, so a `markDirty` landing in a read-push-clear gap survives. `eraseAll` also clears the outbox on every backend. `LocalDatabase` is the platform provided accessor. `PositionKey` lives in the `:shared` module under the same package name. `DailyActivityStore` is a separate, local-only persistence seam (same Room/IndexedDB/in-memory triad) for `DailyActivityRecord`, one row per local calendar date; only `proj.memorchess.axl.core.streak.StreakTracker` is expected to touch it.
- **`data/explorer/`** — the Lichess opening explorer panel. `LichessExplorerClient` calls the API, `LichessExplorerResponse` decodes it, `ExplorerCache` persists responses keyed by `(fen, source)`, `CachedExplorer` combines the two, `ExplorerSource` selects the database queried, and `ExplorerViewModel` drives the panel.
- **`data/repertoire/`** — the downloadable repertoire catalog. `RepertoireCatalogClient` fetches `manifest.json` and the PGN files it lists, accepting `schemaVersion` 1 only. `RepertoireManifest` and `RepertoireDescriptor` are that contract, `RepertoireColor` the side taught, `CatalogResult` the typed outcome so callers never inspect Ktor exceptions, `CachedRepertoireCatalog` the stale cache fallback, `InstalledRepertoireStore` the installed id set (persisted in `INSTALLED_REPERTOIRES_SETTING`), and `RepertoireLibraryViewModel` the library page driver. `RepertoireMastery` is the "N of M positions solid" snapshot per repertoire for the Today page, and `placeholderRepertoireMastery()` stands in for it until #292 tags positions by their source repertoire.
- **`data/study/`** — Lichess study import. `LichessStudyClient` downloads a public study as parsed PGN, `LichessStudyImporter` runs the end to end import into the opening graph.
- **`scheduling/`** — `SchedulingAlgorithm` is the algorithm interface; `Fsrs6SchedulingAlgorithm` is the active FSRS 6 implementation. `CardState` holds per-card state (`dueDate`, `lastReview`, `firstReview`, `stability`, `difficulty`, `reps`, `lapses`) and `ReviewGrade` is the cross-algorithm rating enum (`AGAIN`, `HARD`, `GOOD`, `EASY`).
- **`streak/`** — `StreakTracker` is the single chokepoint over `DailyActivityStore`: it exposes `streakDays()` and `cardsCompletedToday()` and is what `TrainingScheduler.grade()` feeds on a position's first review of the local day. Local only, rolling over at local midnight; no cross-device sync.
- **`config/`** — `ConfigItem` is the typed persisted-setting abstraction (with `DurationBasedConfigItem` and `EnumBasedAppConfigItem` specializations). The concrete settings are top-level `val`s in `StandardAppConfig.kt` (user-facing) and `InternalAppConfig.kt` (not exposed in Settings); `ALL_SETTINGS_ITEMS` backs the reset flow. `SettingSyncMetadataStore` holds a setting key's four sync fields as sibling keys in the same `Settings` store the value itself lives in (settings never go through `DatabaseQueryManager` for their value, though `DirtyKey.SettingKey` shares the same outbox as nodes and edges); every `ConfigItem.setValue` and `reset()` stamps inline (both are synchronous; only the outbox `markDirty` call is fired on a dedicated background scope, `SETTINGS_SYNC_SCOPE`). `reset()` stamps a tombstone (`isDeleted = true`): it changes the effective value back to the default, and the sync metadata has to change whenever the effective value does.
- **`sync/`** — `DeviceIdentity` is the per install opaque id plus the monotonic write counter (`deviceSeq`) every synced row is stamped with; `persisted` backs it with `Settings` (surviving restarts), `ephemeral` is for throwaway stores. No `SyncEngine` here yet — see `graph/` and `data/`.
- **`auth/`** — Lichess OAuth over PKCE: `LichessOAuthClient`, `LichessSignInController`, `OAuthTokenStore`, `PkceGenerator`, and the platform-provided `OAuthLauncher`.
- **`pgn/`** — PGN import pipeline: `PgnParser` → `PgnGame` → `PgnImporter`, with `PgnImportPreview` and `PgnImportSummary` for the UI and typed `PgnParseException`/`PgnImportException` failures. `PgnParser`, `PgnGame` and `PgnParseException` live in the `:shared` module under the same package name, because the server validates uploaded PGN with the same parser the client validates a download with. `PgnImporter` stays here because it writes through `TreeStore`.
- **`date/`** — `DateUtil`, the date helpers shared across the codebase.
- **`util/`** — small shared helpers (`CanDisplayName`, `Reloader`).
